# 개발 일지 — 어려웠던 점과 해결 과정

처음 목표는 단순했다. 카메라로 작업자의 얼굴을 찾고, 가까워지면 경고하고, 위험하면 컨베이어 벨트를 멈추는 것이었다. 코드도 이미 있었고 Jetson도 준비되어 있었다. 그런데 실제로 장비 위에서 돌려 보니, 코드를 짜는 것보다 "지금 무엇이 어디서 실행되고 있는지"를 아는 것이 훨씬 어려웠다.

가장 먼저 부딪힌 문제는 `No module named 'Jetson'` 오류였다. 코드를 몇 번이나 고쳐도 같은 오류가 났는데, 원인은 코드가 아니었다. VS Code에서 Jetson에 연결했다고 생각했지만, 실제로는 Windows PC의 Python으로 실행하고 있었다. SSH 설정 파일에는 존재하지 않는 호스트 이름이 적혀 있었고 접속 아이디도 빠져 있었다. 설정을 고치고 왼쪽 아래에 `SSH: jetson`이 뜨는 것을 확인한 뒤에야 비로소 Jetson에서 코드가 돌았다. 오류 메시지를 보고 바로 코드를 고치기보다, 먼저 실행 위치부터 확인해야 한다는 것을 배웠다.

다음은 벨트가 돌지 않는 문제였다. 코드와 핀 번호는 맞았지만 벨트는 움직이지 않았다. 카메라 없이 모터만 돌리는 시험 파일을 따로 만들어 실행해 보니 `Device or resource busy` 오류가 났다. 이전에 실행한 프로그램이 터미널 뒤에서 계속 돌면서 GPIO 핀을 잡고 있었던 것이다. 그 뒤로는 문제가 생기면 "지금 핀을 누가 쓰고 있는지"부터 확인했다. 핀에서 실제로 신호가 나가는지 값을 다시 읽어 보는 방법도 이때 썼다. 소프트웨어가 신호를 정상으로 보내는지를 먼저 확인하고 나서야 하드웨어 문제와 코드 문제를 나눌 수 있었다.

가장 헷갈렸던 것은 벨트가 반대로 움직이는 문제였다. 빨강(위험)일 때 벨트가 돌고, 초록(정상)일 때 멈췄다. 처음에는 코드가 틀렸다고 생각했지만, 상태별로 각 핀에 어떤 값이 나가는지 표로 정리해 보니 코드는 의도대로 신호를 보내고 있었다. 실제 배선을 확인하자 원인이 보였다. 모터 드라이버(L9110S)의 입력 두 개 중 하나만 Jetson에 연결되어 있었고, 연결되지 않은 입력은 기본값 HIGH로 떠 있었다. L9110S는 두 입력이 서로 다를 때만 모터를 돌리기 때문에, 우리 배선에서는 33번 핀을 LOW로 내려야 벨트가 돌았다. 배선을 바꾸는 대신 코드를 배선에 맞췄고, 이 이유를 코드 맨 위 주석에 자세히 적어 두었다. 나중에 누가 봐도 왜 LOW가 "작동"인지 알 수 있게 하기 위해서였다.

요구사항을 잘못 이해한 일도 있었다. 계획서에는 "경고 시 작동 정지"라고 적혀 있어서, 처음에는 경고(노랑)에서도 벨트를 멈추도록 만들었다. 그런데 실제로 원한 것은 "경고는 파란 LED로 알리기만 하고, 빨강일 때만 멈춘다"였다. 이 차이 때문에 시험을 몇 번 다시 해야 했다. 문서에 적힌 문장과 실제로 원하는 동작이 다를 수 있으니, 상태별 동작을 표로 만들어 직접 확인받는 것이 훨씬 빠르다는 것을 배웠다.

비전 쪽에서는 상태 깜빡임이 가장 큰 문제였다. 경고 거리(50~200cm)에서는 얼굴이 작게 찍혀서 검출이 프레임마다 끊겼다. 그때마다 상태가 정상과 경고 사이를 오가며 벨트가 덜컥거렸다. DB에 쌓인 로그 1,716건을 분석해 보니, 상태 전환 1,661번 가운데 1,353번(81.5%)이 1초 안에 다시 뒤집혔다. 그래서 "더 위험해지는 쪽은 즉시 바꾸고, 안전해지는 쪽은 1초 동안 계속 유지될 때만 바꾼다"는 안정화 필터를 넣었다. 적용 후에는 이 비율이 16.7%로 줄었다. 남은 것은 모두 경고에서 위험으로 바뀌는, 즉시 반영해야 하는 전환이었다. 다만 필터 적용 후 로그는 39건뿐이라, 이 숫자는 아직 예비 결과로 보고 있다.

대시보드를 연결할 때는 이전에 만들어 둔 HTML 대시보드에서 숨은 버그를 찾았다. 일반 사용자 권한으로 실행하면 항상 나오는 무해한 경고(`/dev/mem` 점검 생략)를 핀 설정 오류로 오인해서, 대시보드는 지금까지 한 번도 모터를 움직이지 못했다. 진짜 오류일 때만 멈추도록 고친 뒤에야 하드웨어 제어가 동작했다. 또 카메라는 한 프로그램만 열 수 있어서, 비전 프로그램과 대시보드를 따로 돌리면 서로 충돌했다. 결국 `convey_vision.py` 하나가 카메라, 판단, 제어, 기록을 모두 맡고 대시보드는 같은 프로그램 안에서 화면과 기록만 보여주도록 구조를 합쳤다. 이 과정에서 "AI 판단과 장치 제어는 한 곳에서만 하고, 대시보드는 보여주기만 한다"는 역할 구분도 분명해졌다.

시연을 준비하면서 대시보드 화면도 다듬었다. 상태 줄의 글자만으로는 멀리서 현재 상태를 알아보기 어려워서, 카메라 아래에 빨강(위험·정지), 노랑(경고·작동), 초록(정상·작동) 신호등을 넣었다. 노랑은 실제 장비에서 브레드보드의 파랑 LED에 해당한다는 설명도 함께 적었다. 그런데 신호등을 넣고 보니 카메라 화면이 화면 폭에 맞춰 커지면서 신호등이 화면 아래로 밀려나, 시연 영상을 찍으면 카메라·신호등·로그가 한 번에 보이지 않았다. 카메라 높이를 브라우저 창 높이에 맞춰 줄이고 로그 표 높이도 창에 맞추자, 세 가지가 스크롤 없이 한 화면에 들어왔다. 기능이 동작하는 것과 발표에서 한눈에 보이는 것은 다른 문제라는 것을 알게 됐다. 그 뒤 노랑 LED를 구해서 브레드보드의 파랑 LED를 같은 31번 핀에 노랑 LED로 바꿨다. 이제 실제 LED 색과 대시보드 신호등 색이 같다.

마지막 주에는 세 가지 요청을 반영했다. 첫째, 대시보드가 Jetson 안에서만 열려 다른 곳에서 볼 수 없었다. 같은 Wi-Fi에서는 주소만 열면 되도록 바꾸고, 인터넷에서는 Cloudflare 임시 터널로 https 주소를 만들었다. 그런데 주소만 알면 누구나 종료 버튼으로 벨트를 멈출 수 있다는 점이 걸려서, 처음에는 접속 자체에 비밀번호를 걸었다가, 시연 때 누구나 바로 볼 수 있어야 해서 보기는 열어 두고 종료·DB 버튼을 누를 때만 비밀번호를 묻게 바꿨다. 기능을 여는 것과 함께 누가 무엇을 할 수 있는지도 같이 정해야 한다는 것을 배웠다. 둘째, 로그를 기간으로 찾을 수 있게 했다. 처음 시험에서 검색 결과가 바뀌지 않아 버그로 보였는데, 실제로는 Aiven DB 응답이 2~3초 걸려서 결과가 늦게 나온 것이었다. 사용자가 고장으로 오해하지 않도록 누르는 즉시 "검색 중…"을 띄웠다. 셋째, 성능 평가에 Accuracy와 F1, 처리 속도(FPS)가 필요했다. 운영 로그에는 정답 거리가 없어서 이 값들을 계산할 수 없었다. 그래서 줄자로 잰 위치에 서서 프레임마다 판단 결과를 모으는 `evaluate_model.py`를 만들었다. 숫자는 실제로 측정한 뒤에만 문서에 적기로 했다.

예상하지 못한 장애도 있었다. USB 웹캠이 갑자기 프레임을 보내지 않는 일이 두 번 있었는데, 장치에서 직접 영상을 받아 봐도 0장이었다. 소프트웨어로는 복구되지 않았고 USB를 다시 꽂아야 했다. PC와 Jetson을 잇는 USB 케이블 연결이 끊긴 날에는 Wi-Fi 주소로 다시 접속할 수 있도록 SSH 설정을 하나 더 만들었다. 현장에서는 코드 말고도 케이블과 장치가 언제든 문제를 일으킬 수 있다는 것을 몸으로 느꼈다.

마지막으로 다른 AI(그록, 제미나이)에게 결과물 검토를 받았다. 지적을 그대로 따르지 않고 하나씩 실제 코드와 시험 결과에 대조해 보았다. 해상도 고정 같은 제안은 웹캠이 이미 640×480으로 동작하고 있어서 필요 없었다. 거리값에 이동평균을 넣자는 제안은 위험 판단을 늦출 수 있어서 적용하지 않았다. 갑자기 40cm로 다가온 사람이 이전의 300cm 값과 평균되면 정지가 늦어지기 때문이다. 대신 "모니터가 없는 환경에서 실행하면 어떻게 되는가"라는 지적은 직접 시험해 보았다. 그 결과 프로그램이 비정상 종료하면서 벨트 정지 코드가 실행되지 않는다는 한계를 새로 발견했다. 이미 잘 동작하는 코드를 무리하게 바꾸기보다, 실행 조건과 한계로 문서에 정직하게 남기는 쪽을 택했다.

이번 경험을 통해 배운 것은 세 가지다. 첫째, 문제가 생기면 코드를 고치기 전에 원인부터 확인해야 한다. 오늘 겪은 문제의 절반 이상은 코드가 아니라 실행 위치, 남아 있는 프로세스, 배선, 케이블 때문이었다. 둘째, 안전 시스템에서는 "위험해지는 쪽은 즉시, 안전해지는 쪽은 신중하게"라는 비대칭 원칙이 중요하다. 셋째, 결과는 숫자와 기록으로 말해야 한다. 정답 데이터가 없어서 정확도나 mAP는 계산하지 못했지만, 로그로 측정할 수 있는 것만 측정하고 측정하지 못한 것은 "측정 필요"로 남겼다.

아직 남은 과제도 분명하다. 얼굴이 보이지 않는 작업자(뒤돌아선 사람)는 검출할 수 없어서, 사람 전체를 검출하는 모델과 함께 써야 한다. 거리는 얼굴 크기로 추정한 값이라 정답 거리 데이터를 모아 다시 보정해야 한다. 모터 드라이버의 나머지 입력도 연결해 배선을 확정해야 한다. 이번 결과물은 실제 Jetson과 실제 벨트 위에서 감지부터 정지, 기록까지 이어지는 것을 확인했다는 점에서 의미가 있다. 다만 현장에 적용하려면 더 많은 데이터와 검증이 필요하다.
